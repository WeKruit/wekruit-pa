# Phase 11.3 Plan — `mem0UserId` Authoritative Migration

territory under task prompts below.

> Carry-over from 11.1: `buildPersonaCard` is `userId`-keyed and MUST stay

> partition-key swap is **scoped to Mem0/Qdrant payload `user_id` only**.

---

## 1. Identity contract update

This phase amends `11-IDENTITY-CONTRACT.md` §3.2 and §3.3 (no rewrite —
the contract already documents the target shape; the regression is on
the runtime side). Insert the following clarifications inline in the
contract during 11.3.1:

- `userId` (Firestore canonical) remains authoritative for: `pa_users`,
  `pa_messages`, `pa_memory_facts`, `pa_memory_actions`, `pa_memory_events`,
  `pa_turns`, `pa_agent_turns`, `pa_inbound_events`, `pa_outbound`,
  `pa_audit_events`, `pa_safety_events`, **persona card scope**.
- `mem0UserId` is authoritative for the Qdrant payload `user_id` partition
  on collection `pa_memory` (semantic memory only). It is the ONLY surface
  whose key may differ from `userId`.
- Single resolver: `resolveMem0PartitionKey(user) = user.mem0UserId ?? user.id`.
  Lives at `packages/memory/src/identity.ts`. All Mem0/Qdrant call sites
  (production + admin + scripts) MUST pass through this helper. Direct
  `user.mem0UserId` access outside the helper is a lint-grade smell.
- Memory Admin operations (list / delete-point / clear) MUST resolve via
  the helper after migration. Backfill (11.3.3) preserves the equivalence
  `mem0UserId == userId` for legacy users so dashboard behavior is
  byte-identical pre/post migration.
- Phase 12 outreach scheduler: same two-surface scope as the live
  orchestrator turn — `userId` for Firestore and outbound throttling,
  resolved partition for Mem0 recall.
- Phase 13 matching connector: `userId`-only. Phase 13 does NOT touch
  Mem0/Qdrant directly (per A4). When Phase 13 needs semantic recall, it
  calls `loadPersonalizationContext` which already handles the resolver.

## 2. Migration phases

Three deploys, ordered. Each deploy is independently safe to roll back.

**Deploy 1 — Backfill (data-only, no code path swap).**
- Run `scripts/pa-backfill-mem0-user-id.mjs --apply`.
- For every `pa_users.{id}` document where `mem0UserId` is unset (or
  empty string), write `mem0UserId = id`.
- Idempotent: if `mem0UserId` is already set to ANY non-empty value
  (whether equal to `id` or operator-set), the script leaves it alone.
- Outcome: production reads/writes are unchanged because the runtime
  still uses `userId` directly.

**Deploy 2 — Resolver in code (read-path swap, behind kill switch).**
- `mem0Search`, `mem0Add`, `clearUserMemory` accept and use the resolved
  partition key.
- Orchestrator + admin CF compute the partition via the helper and pass
  it through.
- Kill switch: env `PA_MEM0_USE_PARTITION_KEY` defaults to `true`; setting
  to `false` reverts every call site to `user.id`. Single-flag rollback
  during incident, no redeploy needed (Cloud Functions env var change is
  ~30s propagation).
- Outcome: behavior identical to Deploy 1 because backfill made
  `mem0UserId == userId` for everyone.

**Deploy 3 — Memory Admin CF rewire + drift telemetry.**
- `apps/functions/src/index.ts` `memoryAdmin` GET/DELETE/POST resolve the
  partition before calling `listQdrantMemories` / `deleteQdrantPointForUser`
  / `clearUserMemory`.
- Drift logging emits `pa_audit_events` row when
  `resolveMem0PartitionKey(user) !== user.id`.
- Outcome: dashboard now hits the resolved partition; identical to legacy
  for backfilled users. Reseated / future-rebound users (where
  `mem0UserId !== userId`) work correctly — the ONLY net behavior change.

## 3. Tasks (P8 prompts, six-element)

Each task lists: WHY · WHAT · WHERE · HOW MUCH · DONE · DON'T.

### 11.3.1 — `resolveMem0PartitionKey` helper + unit tests

- **WHY**: Single source of truth for the partition key. Prevents drift
  between mem0.ts, admin.ts, orchestrator, scripts.
- **WHAT**: Pure function `resolveMem0PartitionKey(user: Pick<User, "id" |
  "mem0UserId">): string` returning `user.mem0UserId?.trim() || user.id`.
  Empty-string `mem0UserId` is treated as unset (defensive — Firestore
  snapshots sometimes return `""` for cleared optional strings).
- **WHERE**: `packages/memory/src/identity.ts` (new file).
  `packages/memory/src/index.ts` exports it.
  `packages/memory/src/identity.test.ts` (new, ≥6 cases).
- **HOW MUCH**: ≤60 LOC src + ≤80 LOC test. No external deps.
- **DONE**:
  1. `npm test -w @pa/memory -- identity` passes ≥6 cases:
     unset, set-to-userId, set-to-different, empty string, whitespace,
     `mem0UserId` set on a user with no `id` (must throw `TypeError`).
  2. `npm run build -w @pa/memory` clean.
- **DON'T**: do NOT read Firestore. Do NOT log inside the helper (drift
  logging is a separate concern in 11.3.7). Do NOT take a `Firestore`
  arg. Do NOT export from any package other than `@pa/memory`.

### 11.3.2 — User schema marker + Firestore index review

- **WHY**: `mem0UserId` becoming authoritative needs explicit schema
  documentation; dashboard queries that filter by `mem0UserId` (none
  today, but Phase 12/13 may add) need an index decision recorded.
- **WHAT**:
  1. Update `UserSchema.mem0UserId` JSDoc in
     `packages/core-types/src/index.ts` to call out: "Authoritative for
     Mem0/Qdrant partition. Use `resolveMem0PartitionKey(user)` from

  2. Inventory: `grep -rn "where.*mem0UserId" apps packages` — confirm
     no current Firestore query filters on this field. Record finding

     to revisit if matching connector queries by partition".
- **WHERE**: `packages/core-types/src/index.ts` (JSDoc only, no schema
  shape change). `firestore.indexes.json` untouched in this task.
- **HOW MUCH**: ≤15 LOC delta.
- **DONE**: schema build clean, JSDoc visible in `dist/index.d.ts`.
- **DON'T**: do NOT make `mem0UserId` required. Do NOT add a composite
  index speculatively (YAGNI; Phase 13 will know what it needs).

### 11.3.3 — Backfill script `scripts/pa-backfill-mem0-user-id.mjs`

- **WHY**: Existing users have `mem0UserId === undefined`. After Deploy 2
  the runtime resolves to the same value, but we need explicit data so
  audit trails and Phase 12/13 can rely on the column being populated.
- **WHAT**: Idempotent script with `--dry-run` (default) and `--apply`.
  - Iterates `pa_users` in pages of 200.
  - For each doc: if `mem0UserId` is non-empty string → skip (count as
    `preserved`).
  - Else → set `mem0UserId = doc.id`, `updatedAt = new Date().toISOString()`.
  - Writes a summary line to stdout: `scanned=N preserved=K updated=M
    skipped_no_id=0`.
  - Re-running `--apply` after a successful run reports `updated=0`.
- **WHERE**: `scripts/pa-backfill-mem0-user-id.mjs` (new). Pattern after
  `scripts/pa-clear-user.mjs` for Firestore admin init.
- **HOW MUCH**: ≤120 LOC.
- **DONE**:
  1. Dry-run on prod (read-only) reports a non-zero `updated` count
     equal to "users without mem0UserId today".
  2. After `--apply`, second dry-run reports `updated=0`.
  3. Operator-set `mem0UserId` rows untouched (manually verify with one
     synthetic user where `mem0UserId="custom_partition_x"` before the
     run).
- **DON'T**: NEVER overwrite a non-empty `mem0UserId`. NEVER write to any
  other field besides `mem0UserId` and `updatedAt`. NEVER touch Qdrant.

### 11.3.4 — `mem0Search` / `mem0Add` rewire to partition key

- **WHY**: Make the read/write path use the resolved partition.
- **WHAT**:
  1. Extend `LoadContextInput.mem0UserId` and `AfterTurnInput.mem0UserId`
     JSDoc — drop "advisory, ignored" wording.
  2. In `loadPersonalizationContext` use
     `input.mem0UserId ?? input.userId` for the `mem0Search` call.
  3. In `afterAssistantTurn` use `input.mem0UserId ?? input.userId` for
     the `mem0Add` call.
  4. Kill switch: env `PA_MEM0_USE_PARTITION_KEY` (default unset = on).
     When literal string `"false"` → fall back to `input.userId`. Read
     once per call (no module-level cache; Cloud Functions cold start
     handles the env update).
- **WHERE**: `packages/memory/src/stacked.ts`,
  `packages/memory/src/types.ts` (JSDoc), `packages/memory/src/stacked.test.ts`.
- **HOW MUCH**: ≤40 LOC src + ≤120 LOC test.
- **DONE**:
  1. New unit tests assert `mem0Search` and `mem0Add` are called with
     the resolved partition when caller supplies `mem0UserId`.
  2. Test for kill switch: `PA_MEM0_USE_PARTITION_KEY=false` collapses
     to `userId` even when partition differs.
  3. Existing memory-recall scenario suite still passes after build.
- **DON'T**: do NOT change `mem0Search`/`mem0Add` signatures (they still
  take `userId: string` — caller resolves and passes the partition string
  positionally). Do NOT introduce a third partition key. Do NOT log
  drift here (11.3.7).

### 11.3.5 — `clearUserMemory` partition rewire

- **WHY**: Same partition swap on the admin clear path.
- **WHAT**:
  1. Add `mem0PartitionKey?: string` to `ClearUserMemoryOptions` (NOT a
     required arg — preserves binary compatibility for the in-band reset
     trigger that doesn't have a `User` handy).
  2. `clearQdrantForUser` uses `mem0PartitionKey ?? userId` for the
     Qdrant filter `user_id`.
  3. Firestore deletes still scope on `userId` (Firestore docs are
     `userId`-keyed; this is a hard line from the contract §3.1).
- **WHERE**: `packages/memory/src/admin.ts`,
  `packages/memory/src/admin.test.ts`.
- **HOW MUCH**: ≤30 LOC src + ≤60 LOC test.
- **DONE**:
  1. Unit test: when `mem0PartitionKey="X"` and `userId="Y"` are both
     supplied, Qdrant filter is `user_id=X` and Firestore queries filter
     by `userId=Y`.
  2. Backward compat test: omitting `mem0PartitionKey` produces today's
     behavior (`user_id=userId`).
- **DON'T**: do NOT change Firestore-scope to use the partition key. Do
  NOT remove the existing positional `userId` argument.

### 11.3.6 — Memory Admin Cloud Function rewire

- **WHY**: Dashboard list/delete/clear must hit the resolved partition.
- **WHAT**: in `apps/functions/src/index.ts` `memoryAdmin` handler:
  1. After validating `userId`, fetch `pa_users.{userId}`. If missing →
     `404 user_not_found` (today's behavior is to silently query Qdrant
     with a non-existent partition; tighten this).
  2. Resolve via the helper.
  3. GET → `listQdrantMemories(partitionKey, ...)`.
  4. DELETE → `deleteQdrantPointForUser(partitionKey, pointId)`.
  5. POST clear → `clearUserMemory(userId, deps, { ...,
     mem0PartitionKey: partitionKey })`.
  6. Response payload includes both `userId` and `mem0PartitionKey` so
     the dashboard can render drift indicators.
- **WHERE**: `apps/functions/src/index.ts` (only the `memoryAdmin`
  handler + the two helpers `listQdrantMemories` /
  `deleteQdrantPointForUser` get partition-key arguments renamed).
- **HOW MUCH**: ≤60 LOC delta.
- **DONE**:
  1. Build clean (`npm run -w apps/functions build`).
  2. Manual REST call (curl) against staging: GET returns same point set
     for a backfilled legacy user as it did pre-deploy.
  3. Manual REST call: synthetic user with `mem0UserId="alt_x"` returns

- **DON'T**: do NOT touch the dashboard frontend in this task. Do NOT
  introduce a new endpoint. Do NOT bypass `requireDashboardAdmin`.

### 11.3.7 — Drift telemetry

- **WHAT**: emit a `pa_audit_events` row with

- **WHERE**: `packages/memory/src/identity.ts` adds an exported

- **HOW MUCH**: ≤80 LOC src + ≤80 LOC test.
- **DONE**:
  1. Unit test: helper writes an audit row when keys differ.
  2. Unit test: helper does NOT write when keys match.
  3. Unit test: Firestore write failure is caught — the caller never

- **DON'T**: do NOT throw on drift. Do NOT block the turn. Do NOT spam

## 5. Rollout strategy + rollback flags

- **Kill switch**: `PA_MEM0_USE_PARTITION_KEY=false` reverts the
  mem0Search / mem0Add / clearUserMemory call sites to legacy
  `user.id`-keyed behavior. Single env var, no redeploy.
- **Backfill rollback**: NOT required. Setting `mem0UserId = userId`
  for legacy users is forward-compatible with both the kill-switch-on
  and kill-switch-off code paths (resolver returns `mem0UserId` which
  equals `userId`; legacy code uses `userId` directly — same string).
- **Dashboard CF rollback**: revert apps/functions deploy. The
  resolver-on memory layer still works against the legacy
  dashboard call shape because `mem0UserId == userId` for all
  backfilled users.
- **Hard rollback** (only if Qdrant points end up split across two
  partitions due to a bad backfill): clear the `alt` partition via
  `clearUserMemory(userId, { mem0PartitionKey: "alt" })`, fix backfill
  logic, re-run.
