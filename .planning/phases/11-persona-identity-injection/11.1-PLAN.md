# Phase 11.1 Plan — Persona Card Injection (Firestore-only)

> Status: P9-B v1, low-risk first chunk of Phase 11.
> Scope: ONLY 11.1. Mem0 partition authority (was 11.2/11.3) stays
> serialized. Markdown only — production code is P8 territory.

## 0. Architecture lock (carry-forward, do not relitigate)

- Persona card is **Firestore-only**, built from `MemoryFact` rows where
  `status === "confirmed"` (sources: `explicit_user`, `operator`, or
  admin-confirmed `proposal`). Never read from Mem0/Qdrant.
- Card is a separate `system` AgentInputItem ordered **before** the Mem0
  recall block. Both can be present, persona-only, recall-only, or
  neither.
- Empty fact set → no card injected (no empty heading).
- Pure read-only orchestrator-side load + format. No SDK tool ever
  reads persona; no LLM round-trip mediates persona assembly.
- `mem0UserId` semantics are NOT touched here. `userId` is the only key
  persona uses.
- Existing `systemInputs` path stays — persona card is an addition,
  never a replacement of the orchestrator surface.
- `webSearchTool` (current-info) and `remember-fact` MUST keep working
  unchanged after persona card lands.

## 2. Tradeoff for 11.1.3 (decision recorded here)

The current `memoryBlockWithFacts(memoryBlock, facts)` helper concatenates
confirmed facts and Mem0 recall into one string consumed by both the
default Agents SDK path (`systemInputs`) AND the chat.completions
fallback path (`memoryBlock` field, emergency rollback only).

**Two options:**

- **(a) Keep `memoryBlockWithFacts` as a single-string compat path AND
  add `buildPersonaCardSystemInput()` as a separate helper.** Persona
  card becomes its OWN `systemInputs[0]` entry; `memoryBlockWithFacts`
  output remains `systemInputs[1]`. Fallback path keeps receiving the
  legacy concatenated `memoryBlock` field unchanged.
- **(b) Refactor `memoryBlockWithFacts` to emit two separate system
  inputs.** Cleaner long-term but breaks the chat.completions fallback
  surface and entangles the rollback path with the new contract.

**Decision: (a).** Rationale:
- Minimizes blast radius. Chat.completions fallback (`PA_AGENT_RUNTIME=
  chat_completions`) is a kill-switch path; we do not modify its
  contract here.
- Persona card gets explicit ordering control as a distinct
  `systemInputs` entry.
- Rollback flag (`PA_PERSONA_CARD_DISABLED=true`) becomes a 1-line guard
  that skips appending the persona entry — the rest of the path is
  untouched.

P7 implements option (a). Option (b) is deferred until Phase 11.3 or
later when the fallback path is itself reviewed.

## 3. Tasks (P8 prompts, six-element form)

### 11.1.1 — `buildPersonaCard` helper (pure function)

- **WHY (Goal):** Provide the deterministic, Unicode-safe persona-card
  builder. Closes the "deterministic" half of CONTEXT Criterion 1.
- **WHAT (Inputs):** `MemoryFact[]`. No Firestore handle, no I/O.
- **WHERE (Scope):** create `packages/memory/src/persona-card.ts` and
  `packages/memory/src/persona-card.test.ts`. Append a single export
  line in `packages/memory/src/index.ts`. Do NOT touch `facts.ts` or
  `stacked.ts`.
- **HOW MUCH (Contract):**
  - Signature: `buildPersonaCard(facts: MemoryFact[]): string | null`.
  - Filter: keep only `status === "confirmed"`. Discard everything else.
  - Sort: by `createdAt` ascending (lexicographic on ISO is correct);
    tiebreak by `id` ascending.
  - Dedup: by `normalizedFactContent(content)` (reuse the orchestrator
    rule — trim + collapse whitespace) before formatting.
  - Cap: max 20 facts; truncate older-first overflow (keep most recent
    20 after sort). Total formatted card ≤ 1500 chars; if over, drop
    oldest until under cap; if a single fact alone exceeds the cap,
    truncate that fact's content to 200 chars + `…`.
  - Format:
    ```
    Persona facts (confirmed):
    - <fact 1 content>
    - <fact 2 content>
    ```
    (no trailing newline)
  - Empty input or zero confirmed → return `null` (do NOT return the
    bare heading).
  - Unicode: do NOT lowercase, do NOT NFC-normalize beyond what the
    Firestore round-trip already does. Preserve zh/en/ja/emoji as-is.
    Length cap counts JS string length (UTF-16 code units), consistent
    with how the rest of the codebase counts.
- **DONE (Verification):**
  - `npm test -w @pa/memory` passes with new `persona-card.test.ts`
    covering: (1) empty array → null, (2) all-deleted → null,
    (3) two confirmed facts in scrambled `createdAt` produce a stable
    string with deterministic ordering, (4) duplicate `content` after
    normalization is deduped, (5) > 20 facts → 20 emitted, oldest
    dropped, (6) 1500-char cap honored with oldest-first eviction,
    (7) zh + ja + emoji round-trip unchanged.
  - `npm run build:all` clean.
- **DON'T (Red lines):**
  - No Firestore reads. No Mem0 reads. No async. No clock.
  - Do NOT export a default. Named export only.
  - Do NOT inject the heading when the list is empty.
  - Do NOT mutate the input array.
  - Do NOT reach into `MemoryFact.source` to filter — `confirmed` is
    sufficient (operator + explicit_user + admin-promoted proposals
    all qualify; that gate is owned upstream by `facts.ts`).

### 11.1.2 — Wire persona card into the orchestrator default-LLM path

- **WHY (Goal):** Persona card actually reaches the Agents SDK turn,
  ordered before Mem0 recall. Closes CONTEXT Criterion 1 (live agent
  turns include deterministic persona card).
- **WHAT (Inputs):** `packages/pa-orchestrator/src/index.ts` lines
  ~415–435 (the systemInputs construction at the default-LLM call site,
  immediately above `runAgentTurn`). Existing helpers:
  `listConfirmedMemoryFacts`, `memoryBlockWithFacts`, `buildPersonaCard`
  (from 11.1.1).
- **WHERE (Scope):** ONLY `packages/pa-orchestrator/src/index.ts` and
  `packages/pa-orchestrator/src/index.test.ts`. Do not touch
  `agent-runtime` or `memory`.
- **HOW MUCH (Contract):**
  - At the systemInputs build site:
    1. Build `personaCard = process.env.PA_PERSONA_CARD_DISABLED ===
       "true" ? null : buildPersonaCard(facts)`.
    2. Build `recallBlock = memoryBlockWithFacts(mem.memoryBlock, facts)`
       (unchanged behavior — keeps the chat.completions fallback's
       `memoryBlock` field intact).
    3. Compose `systemInputs` as the array of non-null entries IN ORDER:
       `[personaCard, recallBlock ? "Memory context:\n" + recallBlock :
       null].filter(Boolean)`.
  - When persona is non-null and recall is non-null, BOTH appear; persona
    is `systemInputs[0]`, recall is `systemInputs[1]`. Ordering is
    load-bearing — verified by test.
  - When persona is null → systemInputs unchanged from today.
  - When recall is null but persona is non-null → systemInputs has
    exactly the persona entry.
  - The `memoryBlock` field passed to `runAgentTurn` is UNCHANGED (legacy
    chat.completions field). Persona is NOT folded into it.
- **DONE (Verification):**
  - New unit tests in `packages/pa-orchestrator/src/index.test.ts`:
    (a) two confirmed facts + non-null Mem0 block → assert
    `runAgentTurn` mock received `systemInputs[0]` starting with
    `Persona facts (confirmed):\n` and containing both fact contents,
    AND `systemInputs[1]` starting with `Memory context:\nConfirmed user
    facts:`. (b) zero facts + non-null Mem0 → systemInputs has exactly
    one entry (the recall). (c) two facts + null Mem0 → systemInputs has
    exactly the persona entry. (d) zero facts + null Mem0 → systemInputs
    is `[]`. (e) `PA_PERSONA_CARD_DISABLED=true` → persona absent even
    when facts exist; recall present.
  - `npm test -w @pa/pa-orchestrator` passes.
  - `npm run build:all` clean.
- **DON'T (Red lines):**
  - Do NOT change the `runAgentTurn` adapter signature.
  - Do NOT inject persona into `agent.systemPrompt` (persona is data,
    not agent config; A2 boundary).
  - Do NOT remove or alter `memoryBlockWithFacts` in this task — that
    is 11.1.3's surface (and per the recorded tradeoff above, even
    11.1.3 keeps it intact).
  - Do NOT touch any tool plumbing (`buildTurnTools`, `webSearchTool`,
    `remember-fact`). Verify by running the existing current-info-live
    and memory-recall scenarios as part of pre-merge gate.
  - Do NOT add a second Firestore read for facts; the existing
    `store.listMemoryFacts(event.userId)` result is the input.

## 5. Rollback plan

Single env flag: `PA_PERSONA_CARD_DISABLED=true`.

- 1-line orchestrator guard (in 11.1.2): when set, `personaCard` is
  forced to `null`, and `systemInputs` reverts to exactly the legacy
  shape (recall-only, or empty).
- No redeploy required — Cloud Functions env var change + restart.
- Mem0 recall path, `webSearchTool`, `remember-fact` connector, and
  `__PA_RESET__` guard are all untouched by the rollback flag.
- Forward path: once persona card is proven stable for ≥1 week in prod
  with the flag unset (default), Phase 11.3 may collapse the env guard.
  Until then it stays.

## 6. Risk register

| Risk | Severity | Mitigation |
|---|---|---|
| **System input ordering** — SDK could reorder system inputs internally | HIGH | `buildAgentsInputItems` (`openai-agents-adapter.ts:134`) iterates `ctx.systemInputs` in array order and emits each as a discrete `system` item; verified by code read. 11.1.2 unit test asserts `systemInputs[0]` is persona, `[1]` is recall — if SDK ever reorders we'll catch it in the integration scenario, not at the unit boundary. |
| **Token-budget blow-up** — persona on every turn | MEDIUM | 11.1.1 caps: ≤ 20 facts, ≤ 1500 chars total, oldest-first eviction. At 1500 chars the per-turn delta is ~400 tokens worst case; tracked via `pa_turns.usage.inputTokens`. If p95 input tokens jumps > 1000 over 10.5 baseline, flip rollback flag. |
| **Cache warmth / latency** — every turn now reads facts + Mem0 + persona | MEDIUM | Persona card consumes the SAME `facts` array `store.listMemoryFacts(event.userId)` already loads (one Firestore read; no additional read). Mem0 recall and FirestoreSession history reads are unchanged. Per-turn read count: unchanged (1 facts read + 1 history read + 1 Mem0 search; persona is a pure transform of facts). Latency budget is preserved. |
| **Empty-card heading regression** — early refactor accidentally injects empty `Persona facts (confirmed):` heading | LOW | 11.1.1 test (1) and (2) explicitly assert `null` return; reviewed at PR. |
| **Tool regression** — persona injection breaks `webSearchTool` or `remember-fact` | MEDIUM | 11.1.2 pre-merge gate runs current-info-live-zh + memory-recall-zh + persona-card-zh in the harness suite. Allowlist + budget plumbing is untouched (`buildTurnTools` unchanged). |
| **Identity drift** — persona card on a wrong `userId` | LOW | Persona uses `event.userId` (Firestore canonical). `mem0UserId` is not consulted. Drift is a Mem0-side problem owned by Phase 11.3. |

## 8. Phase 11.3 sequencing

Phase 11.3 (`mem0UserId` authoritative migration, HIGH risk) stays
**serialized after 11.1**, not parallel. Reasons:
- Both edit `packages/pa-orchestrator/src/index.ts` at adjacent call
  sites (`loadPersonalizationContext` + `afterAssistantTurn`). File-
  domain conflict is real.
- 11.3's drift-logging contract benefits from a clean baseline where
  persona card is already shipping deterministically — it lets us
  attribute any post-11.3 regression to the partition-key change, not
  to persona injection.
- Parallel execution would couple two HIGH-risk surfaces (identity
  partition + persona) into one rollback decision; better to roll back
  one at a time.

11.3 plan document is owed separately by P9-B once 11.1 closes.
