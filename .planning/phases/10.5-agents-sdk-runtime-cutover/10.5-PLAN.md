## Task 10.5.1 — Switch default runtime to Agents SDK

### P8 Task Prompt

**Goal (WHY).** Today `runAgentTurn` only routes to `runOpenAIAgentsTurn` when
`process.env.PA_AGENT_RUNTIME === "openai_agents"` AND no explicit OpenAI
client was passed in. Production has the env unset, so 100% of inbound user
turns still execute `runOpenAITurn` (chat.completions on SiliconFlow). Per
Phase 10.5 architecture lock A1, "one runtime = Agents SDK". Flip the default
so production goes through Agents SDK on SiliconFlow `chat_completions` mode,
which the adapter already configures via `setOpenAIAPI("chat_completions")`.

**Inputs (WHAT you read).**
- `packages/agent-runtime/src/run.ts` (current dispatch).
- `packages/agent-runtime/src/openai-agents-adapter.ts` (already pins
  `chat_completions`, already calls `setDefaultOpenAIKey`, already builds
  input from `memoryBlock + history + userMessage`).
- `packages/agent-runtime/src/openai-provider.ts` (must remain importable as
  test-only helper — `runOpenAITurn`, `runWithOpenAI` continue to exist).
- 10.5-CONTEXT.md "Locked architecture A1, A3".

**Scope (WHERE).**
- Edit only `packages/agent-runtime/src/run.ts`.
- Optionally narrow signature in `packages/agent-runtime/src/openai-agents-adapter.ts`
  to allow opt-out via `process.env.PA_AGENT_RUNTIME === "chat_completions"`
  for emergency rollback. Keep the adapter file otherwise unchanged in 10.5.1.
- Do NOT delete `runOpenAITurn`. It stays as a test utility consumed by
  `openai-provider.test.ts` and any harness that imports it directly.

**Contract (HOW).**
- New `run.ts` behavior:
  1. If caller passes an explicit `openAIClient` arg → still route to
     `runOpenAITurn(ctx, openAIClient)`. This is the test injection door.
  2. Else if `process.env.PA_AGENT_RUNTIME === "chat_completions"` → route to
     `runOpenAITurn(ctx)`. Emergency rollback flag.
  3. Else → `runOpenAIAgentsTurn(ctx)`. New default.
- Azure OpenAI branch: keep current behavior (Azure path stays on
  `runWithOpenAI` because Agents SDK's chat_completions mode does not yet
  cleanly support Azure's api-version query). Note this in a comment.
- Anthropic branch unchanged.

**Verification (DONE).**
- `npm run build --workspace=@pa/agent-runtime` passes.
- `npm test --workspace=@pa/agent-runtime` passes; existing
  `openai-agents-adapter.test.ts` still passes; existing
  `openai-provider.test.ts` still passes (it uses an explicit injected
  client, falls in branch 1).
- `npm test --workspace=@pa/pa-orchestrator` passes. Orchestrator tests that
  rely on `runAgentTurn` either inject an `openAIClient` or stub
  `store.runAgentTurn` directly — both paths must keep working.
- Add one unit test in `packages/agent-runtime/src/run.test.ts` (NEW file)
  asserting: with no explicit client and no env override, `runAgentTurn`
  invokes `runOpenAIAgentsTurn`, not `runOpenAITurn`. Use module mocks.

**Red lines (DON'T).**
- Do not introduce a third agent runtime module.
- Do not remove `runOpenAITurn` exports from `packages/agent-runtime/src/index.ts`.
- Do not change SiliconFlow as the LLM. Decision A3.
- Do not switch Agents SDK to `responses` mode. SiliconFlow does not
  implement `/responses`. Decision A3 + Phase 10 bug #3.

## Task 10.5.2 — Connectors as Agents SDK tools (LLM tool-choice surface)

### P8 Task Prompt

**Goal (WHY).** A1 says one runtime; success criterion #2 of 10.5-CONTEXT
says `current-info` must be invoked through Agents SDK tool-choice, not a
regex pre-router. Today `runOpenAIAgentsTurn` hard-codes
`toolChoice: "none"`. We have to expose the agent's allowlisted connectors
to the SDK `Agent` constructor as `tools`, with each tool internally calling
the existing `runConnector(name, args, ctx)` so the audit/safety/policyReason
chain that Phase 10 hardened still fires.

**Inputs.**
- `packages/agent-runtime/src/openai-agents-adapter.ts` (current adapter).
- `packages/pa-connectors/src/index.ts` (`runConnector`, `connectorRegistry`,
  `CurrentInfoInputSchema`, `CurrentInfoOutputSchema`).
- `packages/pa-safety/src/index.ts` (`canUseConnector`).
- `packages/pa-orchestrator/src/index.ts` (turn dispatch — needs to pass a
  tool resolver into the runtime).
- 10.5-CONTEXT.md A2, A4.
- `@openai/agents` 0.8.x exposes a `tool()` factory: `tool({ name,
  description, parameters: zodSchema, execute: async (args) => ... })`. Read
  the SDK's published types under your `node_modules/@openai/agents` after
  install if anything below is unclear; do not guess.

**Scope.**
- Edit `packages/agent-runtime/src/openai-agents-adapter.ts`:
  - Extend `AgentTurnContext` (in `agent-runtime/src/types.ts`) with an
    OPTIONAL `tools?: AgentTurnTool[]` field. `AgentTurnTool` shape:
    `{ name: string; description: string; parameters: ZodTypeAny; execute: (args) => Promise<unknown> }`.
  - In `runOpenAIAgentsTurn`: if `ctx.tools?.length > 0` AND
    `ctx.agent.toolPolicy !== "none"`, build SDK `tool(...)` instances and
    pass them as `tools: [...]`. Set `toolChoice: "auto"` when tools exist;
    keep `"none"` when no tools.
  - Respect `ctx.agent.toolBudgetPerTurn`: pass it as `maxTurns` /
    `toolChoice` cap if SDK supports; otherwise enforce inside
    each tool's `execute` via a shared in-closure counter (P8 may also
    rely on `runConnector` already counting via `usedThisTurn` if the
    orchestrator passes a mutable counter — see below).
- Edit `packages/pa-orchestrator/src/index.ts`:
  - Add a new helper `buildTurnTools(agent, turnCtx, store, db)` that returns
    `AgentTurnTool[]` for each name in `agent.allowedConnectors ?? []`. Each
    tool's `execute` calls `runConnector(name, args, { db, agent,
    turnId, userId, sessionId, usedThisTurn: counter.value })` and bumps
    `counter.value`. The counter is a closed-over `{ value: 0 }`.
  - For `current-info`, the tool's `parameters` schema MUST be the zod
    `CurrentInfoInputSchema` re-exported from `pa-connectors`, with `nowIso`
    auto-injected by the wrapper before calling `runConnector` (LLM
    shouldn't be expected to know the wall clock; the wrapper sets
    `nowIso = store.nowIso()` and lets the LLM specify `query`, `locale`,
    `location`).
  - Pass `tools` into `store.runAgentTurn({ ..., tools })`.
  - Update `OrchestratorStore.runAgentTurn` typing to accept the new field.
- Edit `packages/agent-runtime/src/types.ts`: add `AgentTurnTool` type and
  optional `tools` field. Re-export `AgentTurnTool` from package index.

**Contract.**
- When `agent.toolPolicy === "none"` → never pass tools to SDK, even if
  caller provides them. This matches existing `canUseConnector` denial.
- Tool `execute` MUST go through `runConnector`, never bypass it. Audit and
  `pa_tool_calls` must show the same shape Phase 10 hardened.
- `runConnector` already filters `policyReason: undefined` and undefined
  audit fields. Do not duplicate that logic in the tool wrapper.
- Tool result returned to the LLM: stringify connector output (compact JSON,
  ≤ 1 KB). The LLM then composes the user-facing reply from that JSON. Do
  NOT format the connector output for the user inside `execute` — that is
  the LLM's job once tools are LLM-driven.
- `suppressOutbound`: tools never enqueue outbound. Outbound enqueue still
  happens in the orchestrator post-turn, gated by `shouldSuppressOutbound`.
  Connectors do not directly write to `pa_outbound`. (Already true — keep
  it true.)

**Verification.**
- `npm run build --workspace=@pa/agent-runtime`
- `npm run build --workspace=@pa/pa-connectors`
- `npm run build --workspace=@pa/pa-orchestrator`
- New unit test `agent-runtime/src/openai-agents-adapter.test.ts`:
  - With `toolPolicy: "allowlist"` and one fake tool, the SDK is invoked
    with `tools: [<one>]` and `toolChoice: "auto"`. (Mock the `Agent` /
    `run` exports from `@openai/agents`.)
  - With `toolPolicy: "none"`, tools are dropped and `toolChoice: "none"`.
- New orchestrator test asserting `buildTurnTools` produces a tool bound
  to `runConnector` whose `execute` audits + writes `pa_tool_calls`. Use
  the existing fake Firestore from orchestrator tests.
- `npm test` (root) green.

**Red lines.**
- Do not call OpenAI hosted tools directly from this adapter. `webSearchTool`
  stays inside `current-info.ts` (A4 boundary) and only fires when the
  LLM picks the `current-info` connector.
- Do not let the LLM call `__PA_RESET__`. There must not be a `reset` tool.
  Decision A6.
- Do not bypass `canUseConnector` (it's invoked by `runConnector`).
- Do not mutate `process.env.OPENAI_BASE_URL` from inside a tool. `current-info`
  builds its own `OpenAI` client (see `current-info.ts`) — that pattern stays.
- Do not pass the user message verbatim as a tool argument. The LLM picks
  the tool args; if it picks a different `query` than the raw user text,
  trust the LLM. (Tools exist precisely so the LLM can reformulate.)

  `filterMemoryWrite` — note: signature takes `userText + assistantText`;
  for the connector path, just check the proposed `content` against
  `UNSAFE_MEMORY_PATTERNS` directly. Add a small helper
  `isUnsafeMemoryContent(text)` exported from `@pa/pa-safety` that uses the
  same patterns. Do not duplicate the regex in the connector.).

  same logic to reject sensitive content; reuse it.
- 10.5-CONTEXT.md success #3, A6.

**Scope.**

  - Define `RememberFactInputSchema = z.object({ content: z.string().min(1).max(500), sensitivity: z.enum(["normal", "sensitive"]).optional() })`.
  - Define `RememberFactOutputSchema = z.object({ ok: z.boolean(), factId: z.string().optional(), conflict: z.boolean().optional(), reason: z.string().optional() })`.
  - Register `"remember-fact"` connector. `execute(input, ctx)`:
    1. `const verdict = shouldRejectMemoryFact(input.content)`. If reject,
       return `{ ok: false, reason: verdict.reason }`. Do NOT throw — the
       LLM should be able to apologize gracefully to the user.

       If a fact with normalized identical `content` exists, return
       `{ ok: true, factId: existing.id, conflict: true }`.

    4. Return `{ ok: true, factId, conflict: false }`.
  - Export `RememberFactConnectorInput` and `RememberFactConnectorOutput`.
- Decision: facts created by this connector are written `confirmed=true`,
  same as the current `handleMemoryCommand("remember")` path. Rationale:
  the user explicitly asked PA to remember; we already auto-confirm
  in the regex path. Phase 11 may revisit this when persona facts land.
  Document this in the connector's `description`.
- No new Firestore schema. Re-uses `pa_memory_facts`.

**Contract.**

  / `listConfirmedMemoryFacts` (A2 — WeKruit owns memory writes through
  the helper module, not raw `db.collection().set`).

  `current-info` via the existing `runConnector` audit chain.
- `recordMemoryAction` (the `"remember"` action in `pa_memory_actions`) is
  still written. Decision: the connector's `execute` calls
  `recordMemoryAction(ctx.db, { userId, action: "remember", status:
  "succeeded", content, factIds: [factId] })` so the dashboard's memory
  events tab keeps working without dual code paths.
- Sensitivity hint from LLM is advisory only. `shouldRejectMemoryFact` is
  authoritative. Don't promote a sensitive write because the LLM said
  "sensitivity: normal".

**Verification.**

- New tests in `packages/pa-connectors/src/index.test.ts`:
  - happy path writes a fact + returns `factId`
  - duplicate content returns `conflict: true` and does NOT write twice
  - sensitive content returns `ok: false, reason: ...` and does NOT write
- `npm test --workspace=@pa/pa-connectors`
- `npm test` (root) green.

**Red lines.**
- Do not delete the regex `parseMemoryCommand` parser yet — Task 10.5.4

**Contract.**

- Script is idempotent: re-running on already-migrated state changes nothing.
- Script never deletes agent records.
- Operator UI (dashboard) `agent persona` editor already exposes

**Verification.**

## Rollout strategy

Single-PR safe? **No.** Two reasons:

1. 10.5.1 (flip default) silently activates 10.5.2's tool surface only if
   the agent record has `toolPolicy: "allowlist"`. If 10.5.5 (migration)
   has not yet run in production, the flipped default agent will reach
   the LLM with no tools, so "最近有啥电影" gets answered from stale
   model knowledge — exactly the failure mode Phase 10 fixed.
2. 10.5.4 (delete regex pre-router) MUST land AFTER 10.5.2 + 10.5.5.
   Otherwise live traffic loses the boundary safety net before the LLM
   has the tool to compensate.

**Recommended sequence** (single deploy window, multi-commit branch):

1. Commit 10.5.1 + 10.5.2 + 10.5.6 + 10.5.7 (runtime flip, tools wired,
   contract documented, regression test). Behavior: same as today, because
   the default agent still has `toolPolicy: "none"` so the LLM has no
   tools and the regex pre-router still fires. This commit is a no-op for
   live users. Deploy + verify scenarios + REST.
2. Commit 10.5.3 + 10.5.5 (remember-fact connector + migration script).
   Run migration script. Now the LLM has tools available, BUT the regex
   pre-routers still short-circuit before the LLM sees the message —
   so the connector is wired but unreached. Deploy. Verify nothing broke.
3. Commit 10.5.4 (delete regex pre-routers). Now LLM tool-choice is the
   only path. Deploy + run live scenario suite + REST verify (10.5.8).

Three deploys, but each is independently rollback-safe. Avoids the all-or-
nothing risk of a mega-PR.

If schedule pressure forces single PR: gate via `PA_AGENT_RUNTIME=
"chat_completions"` env override at the function (set on deploy, cleared
after migration runs, re-deployed). That collapses three deploys to two
but introduces a feature flag that must be removed in a fourth deploy —
worse total ops cost.
