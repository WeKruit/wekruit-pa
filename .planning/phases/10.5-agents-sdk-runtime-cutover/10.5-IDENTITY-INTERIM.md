# Phase 10.5 — Identity Contract (Interim)

This is a placeholder so Phase 11 work doesn't relitigate identity semantics
while 10.5 is in flight. Phase 10.5 is a runtime cutover; it does NOT touch
identity, persona injection, or `mem0UserId` authoritative migration. Those
land in Phase 11.

## Pinned facts (do not change in 10.5)

- **`userId` is canonical.** Every Firestore collection
  (`pa_users`, `pa_messages`, `pa_memory_facts`, `pa_memory_actions`,
  `pa_outbound`, `pa_tool_calls`, `pa_audit_events`, `pa_inbound_events`,
  `pa_turns`) keys to `pa_users/{userId}`. Phase 10.5 plumbs `userId` into
  every tool's `ConnectorContext` unchanged. Tools see the same `userId`
  the orchestrator sees on the inbound event.
- **`mem0UserId` stays advisory.** `pa_users.mem0UserId` may exist for
  some users, may be missing for others. Phase 10.5 does NOT introduce a
  new dependency on `mem0UserId`. Mem0 recall uses whatever id the
  existing `loadPersonalizationContext` resolves; that resolution does not
  change in this phase.
- **Persona card injection is deferred.** The `pa_users.persona` /
  `pa_memory_facts` → "Confirmed user facts" path that
  `memoryBlockWithFacts` builds today continues to flow through
  `buildAgentsInput`'s `Memory context:` section. Phase 11 will replace
  this with a structured persona card and possibly a separate system
  message. Don't preempt that decision in 10.5.

## What Phase 10.5 promises Phase 11

- The Agents SDK `Agent` constructor receives `instructions: ctx.systemPrompt`
  unchanged. Phase 11 may replace that with a composed prompt
  (system + persona + memory). The 10.5 wiring leaves room for it because
  `systemPrompt` is just a string the orchestrator owns.
- The connector-as-tool surface (`AgentTurnTool[]`) is extensible — adding
  `recall-memory` or other identity-aware connectors in Phase 11 does not
  require adapter changes. Just register the connector and add to the
  default agent's `allowedConnectors`.
- `userId` propagates into every connector via `ConnectorContext`. Phase 11
  identity-aware connectors (e.g. persona-fact reads) inherit this; no new
  plumbing required.
- The Mem0 recall block is documented (10.5.6 contract test). Phase 11 can
  promote it from string concatenation to a structured system message
  without re-discovering the contract.

## What Phase 10.5 does NOT promise Phase 11

- **No `mem0UserId` migration.** If Phase 11 wants `mem0UserId` to become
  authoritative or to be deprecated, Phase 11 owns that. Open question for
  Phase 11: do we backfill `mem0UserId = userId` for all users, or do we
  drop the field and standardize on `userId` everywhere in Mem0
  payloads? Both options are open at end of 10.5.
- **No persona prompt schema.** Phase 11 picks the schema. 10.5 only ensures
  the channel (system prompt + memory block) reaches the LLM through the
  SDK.
- **No identity inference from inbound metadata.** PA still trusts
  `event.userId` resolved upstream. Phase 11 may revisit if multi-channel
  identity (iMessage handle ↔ phone ↔ email) becomes a problem.

## Boundaries that survive every phase

- A2 (P10 lock): WeKruit owns identity. The Agents SDK never imports
  `firebase-admin`. Identity reads/writes go through `runConnector` and
  the `pa-orchestrator` store. Phase 10.5 reinforces this; Phase 11
  must not relax it.
- A6: `__PA_RESET__` is system-only, regex-guarded, never a tool. Identity
  reset is operator authorized, not LLM authorized.
- WeKruit-owned audit: every identity-touching action (memory write,
  memory read summarized as memory block, fact creation by `remember-fact`)
  emits `pa_audit_events` rows. Phase 11 inherits this requirement.

## Open questions for Phase 11 (do not resolve here)

1. Should the Mem0 recall block move from `buildAgentsInput`'s
   concatenated string into a separate SDK system message? Today the SDK
   `Agent` takes single `instructions`, so 10.5 keeps the string. SDK 0.9+
   may expose multi-message instructions cleanly.
2. Does `mem0UserId` get deprecated, backfilled, or stay advisory? Decision
   blocks the persona-fact write path's id authority.
3. Do persona facts (`pa_memory_facts` with `kind: "persona"` if such a
   shape exists) get a dedicated injector or stay merged into
   `memoryBlockWithFacts`?
4. Should `recall-memory` become a tool? 10.5-CONTEXT lists it as
   "optional, future". 10.5 deliberately ships without it because the
   recall block already pre-loads what the LLM would query for.
